## 1. Goal

Make InLove local-first for user content, with no visible regressions:

- Memory photos and videos live in app-private storage (`filesDir/media`). Room stores a RELATIVE path (`media/picked_<ts>.jpg`). Saving a memory never needs the network. Deleting a memory (or the account) also deletes its files.
- Firebase is used only for auth, the pairing handshake, read-only presets, billing/entitlement and App Check; the avatar lives on Cloudflare R2 (D11). Content sync (memories, anniversaries) and media upload are dormant behind one switch, `DataResidencyPolicy`, which is `LOCAL_ONLY` in production. Anniversaries and love milestones are local built-in defaults (D10).
- Backup (D12): the media files plus a secrets-free manifest saying which partner and which memory each file belongs to; the Room database is never backed up.
- Privacy (D13, D14): Settings tells the user that private memories are not leaked, that the company does not store them, and that they should not delete the app's folders.
- Profile UX:
  - remove the "MÁY" chip;
  - every birthday in the app (mine, the partner's in the couple dialog, and the one that arrives with an invite) goes through ONE `Birthday` model and ONE `BirthdayField` (D15): picked from a calendar (year -> month -> day), limited to 1920..current year, no future dates, stored as canonical `dd/MM/yyyy`;
  - the "Ghép đôi cùng người ấy" banner hides once a partner is set up, and a pairing entry stays reachable.
- Remove the duplication this change touches (the two partner columns become one `PartnerCard`; the birthday rule lives in one place).

## 4. Design

### 4a. `DataResidencyPolicy`

New file `app/src/main/java/com/example/domain/DataResidencyPolicy.kt`. It lives in the domain layer because the domain use case reads it:

```kotlin
package com.example.domain

/** Where user content (memories, anniversaries, their media) lives. Auth, the pairing handshake,
 *  presets, billing and App Check are always online and are NOT gated here. */
enum class DataResidency { LOCAL_ONLY, CLOUD_SYNC }

object DataResidencyPolicy {
  // ponytail: compile-time switch; move to Remote Config only if the owner wants a staged rollback.
  val current: DataResidency = DataResidency.LOCAL_ONLY
  val cloudContent: Boolean get() = current == DataResidency.CLOUD_SYNC

  /** The avatar is the one thing stored online (Cloudflare R2, D11). OFF until the owner provisions the public avatar bucket. */
  val avatarsOnR2: Boolean = false
}
```

`avatarsOnR2` is added by T1 together with the rest of the file, so T19 and T21 only READ it and never co-own the file. `DataResidencyPolicyTest` asserts both defaults (LOCAL_ONLY, `avatarsOnR2 == false`).

**Defaults: safe-by-default.** Every gated constructor parameter defaults to `DataResidencyPolicy.cloudContent`, which is `false`. Only one test file opts back in (A18). So `AppServiceLocator`, `InLoveViewModel` (≈70) and `InLoveApplication` need **no edits**: production picks up LOCAL_ONLY through the defaults.

### 4b. `MediaPath`, the cleaner, and the round-trip

New file `app/src/main/java/com/example/data/media/MediaPath.kt`. It is pure Kotlin with `java.io.File` only, so it is JUnit-testable. Signatures:

```kotlin
object MediaPath {
  const val DIR = "media"
  /** `file:` URI or absolute path inside filesDir/media -> "media/<name>"; anything else (https, content:, assets, blank, already relative) unchanged. */
  fun toStored(filesDir: File, raw: String?): String?
  /** "media/<name>" -> "file://" + File(filesDir, it).absolutePath; legacy absolute path / file: / content: / https unchanged. */
  fun resolve(filesDir: File, stored: String?): String?
  /** The file a stored value points at, only if its canonical path is STRICTLY inside canonical filesDir/media: canonical.startsWith(base + File.separator) && canonical != base. Rejects "..", a sibling such as media2, the media dir itself and other dirs. */
  fun ownedFile(filesDir: File, stored: String?): File?
  /** Deletes owned files of [candidates] that no value in [stillReferenced] maps to (compared by canonical path). Returns the count. Never throws: a failed delete is skipped. */
  fun deleteUnreferenced(filesDir: File, candidates: List<String?>, stillReferenced: List<String?>): Int
}
```

- `toStored` does not use `java.net.URI`: it throws on backslashes, and the Robolectric form of `Uri.fromFile` on a Windows host is `file://C%3A%5C…`. It strips the `file:` prefix, percent-decodes with `URLDecoder.decode(s.replace("+", "%2B"), "UTF-8")` (the `Charset` overload needs API 33) and wraps the result in `File(...)`, all inside try/catch; a failure leaves the value unchanged. `File` normalizes `//C:\Users\x`, `/C:/Users/x` and `C:\Users\x` to the same path on Windows, and `///data/x` to `/data/x` on Android, so there is no drive-letter special case. A value is converted only when the file is strictly inside canonical `filesDir/media`.
- Test values are never `"file://"` literals: JUnit tests build them with `File.toURI().toString()`, Robolectric tests with `Uri.fromFile(file).toString()`. The round trip `toStored(filesDir, resolve(filesDir, "media/a.jpg")) == "media/a.jpg"` is a test case.

### 4g. Backup of the media files and the manifest (D12; T18a, T18b)

Goal: after a phone change the user gets back the photo/video files together with which memory each belongs to and which partner it is about, wherever Android's own backup works. Nothing goes to our servers.

**Allow-list (T18b).** `android:allowBackup="true"` (manifest line 20; the `tools:replace` on line 28 stays) and ONE include, `<include domain="file" path="media"/>`, in `backup_rules.xml` and in BOTH `<cloud-backup>` and `<device-transfer>` of `data_extraction_rules.xml`. There is NO `<exclude>` in either file: the two that existed (the database `inlove_database`, the prefs file `inlove_auth_prefs.xml`) were first kept "to document the intent", but with an allow-list they do nothing, and Android lint reports an `<exclude>` outside every included path as a FATAL `FullBackupContent` error (six of them, found after L3; finding L1-lint in section 10), so they were removed. Once a rules file has an `<include>`, the system backs up only the listed paths, so these stay out implicitly: the Room database (A26), every prefs file including the Firebase Auth store (A27), `files/vault` (plain SQLite stashes) and `files/avatars`.

**Encryption (mandatory, A37).** The files must never be copied unencrypted to the cloud. (a) `data_extraction_rules.xml` (API 31+): `<cloud-backup disableIfNoEncryptionCapabilities="true">`, so the cloud copy exists only on a device that can encrypt it (for example a screen lock is set); `<device-transfer>` is unchanged and still works. (b) `backup_rules.xml` (the legacy format, used on Android 11 and lower): its single include is `<include domain="file" path="media" requireFlags="clientSideEncryption"/>`. The documentation does not say whether several includes of the same path with different flags combine, so each rules section has exactly ONE include. `requireFlags` does not exist in the new format, so (a) and (b) are not interchangeable.

**Manifest (T18a).** `filesDir/media/` + `MediaPath.BACKUP_MANIFEST` (= `"memories_backup.json"`; T3 adds the constant, T8b and T18a use it), so the single include covers it. Moshi `@JsonClass(generateAdapter = true)` data classes of their own (A35; no new dependency):
- `MemoryBackupFile(version = 1, savedAt, memories: List<MemoryBackupEntry>)`;
- `MemoryBackupEntry(syncId, title, dateText, note, photoPath, videoPath, location, isFavorite, anniversaryTitle, createdAt, updatedAt, mediaType, durationSeconds, fileSizeFormatted, privacyLevel, relationshipId, authorId, authorName, partnerName)`.

No password, token, PIN or e-mail is written. Paths are written in the relative `MediaPath` form (4b).
- `syncId` is written as `syncId.ifBlank { "legacy_${createdAt}" }` (A40: very old rows can have a blank one), so every entry has a stable key and a restore is idempotent for all of them.
- `partnerName`: for a memory with a `relationshipId` and an `online_relationships` row, the `displayName` of the user (`user1` / `user2`) who is not the `isCurrentUser` uid; else `couple_profile.partner2Name`; else "".
- A pure `snapshot(memories, profile, relationships, users, me, nowMs)` builds the file (unit-tested). A thin writer encodes it to `memories_backup.json.tmp` and renames over the target (atomic). An empty live list deletes the manifest, so a deleted memory leaves no text behind.

**Writer.** One collector in an app-level scope (the `SupervisorJob` + `CoroutineExceptionHandler` pattern `AppServiceLocator` already uses): `combine(dao.getAllSharedMemories(), dao.getCoupleProfile(), dao.observeRelationships())`, `debounce(2_000)`, and inside the block the online users through `getAllOnlineUsersListSync()` and `getCurrentOnlineUserSync()`. `getAllSharedMemories()` is not filtered by `visibleIn`, so rows hidden by an unpair are included. It starts from `InLoveApplication.onCreate` after `AppServiceLocator.initialize(this)`, as one coroutine `if (restoreOnce()) collect()` (see Restore); the early return under Robolectric (A16) keeps it out of tests.

**Restore (once per install).** In the SAME coroutine, `restoreOnce(): Boolean` runs to completion BEFORE the collector starts. It returns "the live table is now authoritative", and the collector starts only on `true`:
1. If the marker `noBackupFilesDir/memories_restore_done` exists, return `true`. `noBackupFilesDir` is never backed up, so a new phone has no marker while `files/media` has come back; an app update keeps its marker, so it never restores again.
2. If the manifest is missing, or cannot be decoded (the decode failure is caught and logged in one line, never a crash; an unreadable file is of no use to anyone and the first snapshot replaces it), write the marker and return `true`.
3. For each entry, in its OWN try/catch, in this order: skip it (counted) unless every non-blank media path is a relative path owned by `filesDir/media` and its file exists; skip it also when `dao.getSharedMemoryBySyncId(syncId)` already finds a row, live or soft-deleted (A40: a restart after a partial restore must not duplicate). Otherwise `dao.insertSharedMemory(entity)` with a fresh `id`, the manifest's `syncId` and `updatedAt`, `pendingSync = false`, NO `sync_outbox` row, `isCloudinaryStored = false` and empty cloudinary fields (the entity default is `true`). One log line reports inserted, skipped and failed counts.
4. Write the marker AFTER the loop and return `true`, unless an entry threw: then write NO marker and return `false`. A crash or kill in the middle of the loop also leaves no marker, so the next start resumes and step 3 skips what is already inserted.
5. On `false` the collector does not start in this process, so it cannot rewrite or delete the manifest from a partial table; the next start retries. The collector also never runs before step 1-4 finished, so it can never overwrite the manifest from an empty table.

**Interaction with existing rules (verified; no change to those files).**
- `visibleIn` (A3): a restored memory whose `relationshipId` is not on the new phone stays hidden until the same relationship arrives from Firestore (the identity tier is always on), then it reappears. This is the unpair hide/restore rule. A memory without a `relationshipId` is visible at once.
- `AccountDataVault` (A36): restored rows are live rows of the CURRENT scope, which is GUEST on a fresh install. The existing "keep guest data" prompt of a new local registration adopts them; a later sign-in into another scope stashes them under the guest stash, and they return on logout. `user_accounts` is not restored, so the user registers or signs in again, and Firebase Auth is excluded, so the user is signed out on the new phone.
- Account deletion: `MediaPath.deleteUnreferenced` removes only its candidates' own files, so T8b deletes `memories_backup.json` explicitly (and the current user's local avatar file, 4h).

**Known limits (documented, not fixed).** (1) The Auto Backup cloud cap is 25 MB per app; above it the cloud backup is silently skipped (device-to-device transfer has no cap), and videos reach it fast. (2) Restore is best effort: the manifest lags the live data by the 2 s debounce plus the backup interval. (3) Vault gap: after a logout the live table holds the guest rows only, so the manifest lists those until the next login restores the stash. (4) The wallpaper also lives in `filesDir/media` and is backed up as a harmless orphan. (5) `partnerName` refreshes on the next memory or relationship change, not on a rename. (6) The system-backup behavior has no device-level proof in this plan (A27). (7) The vault switch is two commits (A39): a switch that takes longer than the 2 s debounce could publish an empty manifest for a moment; the next change rewrites it, and it is not mitigated. (8) No cloud copy on a device without encryption capability (for example no screen lock); device-to-device transfer still works (A37). (9) On API 24-27 the legacy `requireFlags` requirement prevents the backup altogether (the documentation asks for alternate resources, which this plan does not add); the data simply stays on the phone.

**Tests.**
- `BackupRulesTest` (JVM; reads the two XML files and the manifest as text): exactly one `include domain="file" path="media"` in each of the three places, no `database` or `sharedpref` include, `allowBackup="true"`, `disableIfNoEncryptionCapabilities="true"` on `<cloud-backup>`, `requireFlags="clientSideEncryption"` on the single include of `backup_rules.xml`.
- `MemoryBackupTest`: partner resolution (relationship hit, fallback to `partner2Name`, empty); JSON round trip incl. `updatedAt`; a blank `syncId` is written as `legacy_<createdAt>`; garbage decodes to null; an empty list deletes the file.
- `MemoryRestoreTest` (Robolectric + in-memory Room): inserts rows with `pendingSync = false`, no outbox row, `isCloudinaryStored = false` and the manifest's `syncId` / `updatedAt`; skips an entry whose file is missing; no restore when the marker exists; a second run inserts nothing new; a row (live or soft-deleted) with the same `syncId` blocks the insert, so a partial restore resumes without duplicates; an entry whose insert throws leaves NO marker and `run()` does not start the collector (the manifest survives); the marker is written after the loop; a garbage manifest is ignored and the marker is still written; the collector never runs before the restore (a manifest with one entry survives `run()`).

Skipped: an in-app export/import zip, restoring the couple card or anniversaries (built-in defaults, D10), per-scope manifests and a file-existence merge (add when the owner asks).

### 4h. Avatars on Cloudflare R2 (D11; T19, T20, T21)

**Why this is small.** The client never writes `users/{uid}` (A25): an avatar reaches a partner only inside the invite document, and the invite builder already blanks `file:` avatars (`shareableAvatar`) and passes https ones. So the feature is "swap the Room `avatarUrl` from a `file:` path to an https URL once the upload succeeded". No Firestore collection, no `firestore.rules` change, no Room schema change.

**Flag and owner dependency.** `DataResidencyPolicy.avatarsOnR2` is `false` (T1 adds it). While it is false nothing is signed, uploaded or enqueued and the app behaves as today. To turn it on (owner, outward-facing, NOT done by this plan): create a PUBLIC R2 bucket for avatars, create a token with Object Read & Write on both the media bucket and the avatar bucket, set the params `R2_AVATAR_BUCKET` and `R2_AVATAR_PUBLIC_BASE_URL`, run `firebase deploy --only functions`, then change the flag to `true`.

**Backend (T20; `node --test`, no Gradle).**
- New callable `signAvatarUpload` with options `{ region, enforceAppCheck: true, secrets: R2_SECRETS, maxInstances: 10 }` and a body that starts with exactly `const uid = requireUid(request); await limit('signAvatarUpload', uid);` (A29). It is not entitlement-gated: a `free` row in `GATES`, which grows from 8 to 9.
- New `src/avatar.js` (about 40 lines): `parseSignInput` (`contentType` must be `image/jpeg`; `contentLength` an integer in `[1, cfg.limits.avatarMaxBytes]`), the uid must match `[A-Za-z0-9_-]{1,128}`, the fixed key is `inlove_avt_<uid>`, and the result is `{ uploadUrl, headers, publicId, publicUrl }` with `publicUrl = <R2_AVATAR_PUBLIC_BASE_URL>/<key>?v=<nowMs>` (trailing slashes of the base are trimmed). The presigned URL lives 600 seconds (`expiresInSeconds: 600`; `presign` throws a `RangeError` unless the value is an integer in `[1, 604800]`, so the value is a constant of `avatar.js`, not user input).
- `objectStore.signUpload` gets two OPTIONAL parameters, so existing callers are unchanged (A30): `overwrite` (omits `if-none-match: *`) and `cacheControl` (adds a SIGNED `cache-control` header). Avatars use `public, max-age=31536000, immutable`, which is safe because every URL carries a fresh `?v=`. The Android uploader forwards every signed header (verified in `OkHttpMediaUploader.buildPutRequest`). Because the key is fixed per uid and the header is immutable, a copy fetched earlier under an older `?v=` URL stays in a CDN cache and in Coil for up to a year, even after a newer upload or after `purgeAvatar` deleted the object (residue, §12 risk 14).
- `config.js`: `rateLimits.signAvatarUpload = Object.freeze({ max: 10, windowMs: 3600000 })`, `limits.avatarMaxBytes` (1 MB), `avatarPublicIdPrefix: 'inlove_avt_'`.
- Separate PUBLIC bucket: `defineString('R2_AVATAR_BUCKET', { default: '' })` and `defineString('R2_AVATAR_PUBLIC_BASE_URL', { default: '' })`, and a second lazy `createObjectStore` with the same access-key secrets. "Configured" means the bucket is non-empty AND the base URL is an `https://` URL. That check runs BEFORE `createObjectStore` is called, because `createObjectStore` throws a plain `Error('Thiếu cấu hình R2: …')` on any empty parameter, which a client would see as `internal`. When unconfigured, `signAvatarUpload` throws `HttpsError('failed-precondition', 'avatars-not-configured')` and `purgeAvatar` is a no-op, so a missing avatar bucket never breaks or loops account deletion.

### 4j. One `Birthday` model and one `BirthdayField` (D15; T22, T23, T24)

Today a birthday is a bare `String` handled in several places with different rules: the golden `ProfileUtils` functions, the typed field in the couple dialog, the free-text field in my profile, and the remote invite value that is ingested verbatim (A31 lists the sites).

- **T22 `Birthday`** (`ui/util/Birthday.kt`):

  ```kotlin
  @JvmInline
  value class Birthday private constructor(val text: String) {   // canonical dd/MM/yyyy
    val age: Int get() = ProfileUtils.calculateAge(text)
    val zodiac: String get() = ProfileUtils.calculateZodiac(text).first
    companion object {
      const val MIN_YEAR = 1920
      fun parse(raw: String, nowMillis: Long = System.currentTimeMillis()): Birthday? =
        ProfileUtils.normalizeAnniversaryInput(raw.trim(), nowMillis)?.let(::Birthday)
      fun normalize(raw: String, nowMillis: Long = System.currentTimeMillis()): String =
        parse(raw, nowMillis)?.text.orEmpty()
    }
  }
  ```

  The golden functions are called, never edited. **Decision on 1900-1919:** `parse` and `normalize` keep a valid 1900..today date (it is stored data and the golden rule accepts it). `MIN_YEAR = 1920` is the picker's lower bound and the acceptance rule for NEW input in `BirthdayField` only: `DatePickerRules.birthYearRange(todayYear) = Birthday.MIN_YEAR..todayYear`, so T5 depends on T22. A saved "05/05/1910" is therefore read back and saved unchanged, and the picker simply cannot choose it.
- **T23 `BirthdayField`** (`ui/components/BirthdayField.kt`): a thin composable over `InLoveDatePickerField(pickerOnly = true, yearRange, maxDateMillis, minMillis, presets)` (4c) that takes and returns the canonical text. T11 (my profile) and T12 (the partner birthday in `EditCoupleDialogContent`) consume it. Its first step lists every `InLoveDatePickerField(` and `OutlinedTextField` whose label or tag is about a birthday, to confirm A22 (two sites).
- **T24 boundaries**: text enters the model through `Birthday` at the setters and the ingest, with the `String` signatures unchanged (A31):
  - `InLoveViewModel.saveCoupleProfile` (`cleanGirlBirth`, ≈1077).
  - `OnlineCoupleRepository.updateMyProfile`: resolve ONE effective birthday BEFORE the age and zodiac lines (≈236-237 read the RAW `birthDate`, ≈241 trims it): `val effective = Birthday.parse(birthDate)?.text ?: me.birthDate`, with `me` the Room row read at ≈230. Age, zodiac and the stored `birthDate` all use `effective`. A blank or unparsable value therefore keeps the STORED birthday, which protects the couple-dialog rename path (`InLoveViewModel.kt` ≈1153 calls `onlineRepo.updateMyProfile(cleanMe, u.birthDate, …)` with the stored birthday, so a legacy value such as "5/5/95" must survive a rename). ## 12. Risks

1. **Data loss on uninstall or a new phone is accepted by the owner (D13); the backup of D12 reduces it but does not remove it.** The backup is Android's own system backup of an allow-list (`files/media` only) plus a secrets-free manifest (4g), never the Room database. Why: local-auth secrets live in the database (A26) and the Firebase Auth store is a prefs file (A27); neither may leave the device. Limits (T15/A-5 correction: the notice in 4i states only the screen-lock condition, the ~25 MB cap and the "large videos may be left out" caveat after the T15 rewording; the rest stay known limits in 4g):
   - the Auto Backup cloud cap is 25 MB per app, so a larger media folder is silently skipped (device-to-device transfer has no cap);
   - the manifest lags the live data by the 2 s debounce plus the backup interval;
   - vault gap: after a logout the live table holds the guest rows only, so the manifest lists those until the next login restores the stash;
   - the wallpaper file in `media/` is backed up as a harmless orphan;
   - a restored memory whose `relationshipId` is unknown on the new phone stays hidden by `visibleIn` until the same relationship arrives from Firestore;
   - the platform's backup behavior has no device-level proof in this plan (A27), and a restore never recreates the Room rows beyond the memories.
2. **Deleting a file that is still in use.** The wallpaper shares `media/`, and legacy rows mix absolute, `file:` and relative forms. Mitigations:
   - comparison by canonical path;
   - only the deleted memory's (or account's) own values are candidates;
   - hidden rows count as referenced, and so do the guest rows restored by the vault;
   - `ownedFile` refuses anything outside `filesDir/media`;
   - T3, T8a and T8b tests cover each form.
3. **Coupled users stop seeing each other's new memories and anniversaries.** This is visible behaviour (by design, D6). Outbox rows pile up dormant, and media saved now never gets a `cloudinaryPublicId`, so flipping back to CLOUD_SYNC later needs (a) a backfill-upload task and (b) a delete-versus-remote resurrection re-check: `SyncCoordinator.applyRemoteMemory` (≈319-344, merge ≈327-337) can bring back a locally tombstoned row that points at an already deleted file (F4).
4. **The audit plan is APPROVED and executing in another session on the same dirty tree.** U16, U17, U19, U21 and U23 own the files for L4-L8 (and U14 owns the other `SettingsScreen` rows that T17 sits beside). Risks: anchor drift, two sessions running Gradle on one tree, and foreign test breakage. Mitigations: edit-only work (never `git checkout/restore/stash/reset`), anchors on quoted code instead of line numbers, one Gradle process at a time, re-reading the audit log before each wave, and the fold proposals.
5. **Compose tests and Dialog windows (A10).** The Dialog window is verified by precedent (`BadgeRewardNoteTest`), but the picker's `AnimatedContent` has not run in one. If `DatePickerFlowTest` does not idle, report BLOCKED and return to planning (no `InLoveDatePickerContent` fallback).
6. **The privacy selector is misleading while dormant.** "Chỉ hai ta" / COUPLE_ONLY no longer reaches the partner. A signed-out COUPLE_ONLY save is stored PRIVATE (one-way). The Settings notice (4i, T17) now tells the user that memories stay on the phone, but the selector itself is unchanged (4f).
7. **`readOnly` field tap.** A `readOnly` `OutlinedTextField` does not deliver `clickable`. T10 uses the `interactionSource` release approach (with the overlay `Box` as the in-task fallback), and T11's test taps the field itself, not only `${testTag}_calendar_btn`.
8. **R2 media provider (built, uncommitted)** stays wired in `AppServiceLocator` but is unreachable while dormant. Do not delete it; R2-12/13/14 stay deferred.
9. **An invalid legacy birthday is dropped on the next Save.** `Birthday.normalize` keeps every valid date from 1900 to today (stored data; 4j), the picker offers only 1920..today, and a free-text value that does not parse shows blank and is saved blank. A remote invite birthday in another format is normalized at the ingest (T24); an invalid one is stored as blank. The name-only rename path (`InLoveViewModel` couple dialog, which passes the STORED birthday to `updateMyProfile`) must not blank it: the repository keeps the stored value when the incoming one is blank or does not parse (`Birthday.parse(...)?.text ?: me.birthDate`), and T24's test covers that path.
10. **Account deletion irreversibly removes the local photos and videos** (the user's only copy, since nothing is uploaded). No confirmation text changes in this plan; the existing delete-account flow already asks for confirmation.
11. **Baseline test noise.** The full suite is not green today and the failing set rotates per run (the `ChecklistTest` Compose timeout, the AcceptInvite race). Hence the baselines in section 9 and the "listed classes" pass rule.
12. **Leak on failure.** If anything throws between the candidate collect and the delete (memory delete or account deletion), the media files stay on disk but no user data is lost. The deferred orphan sweep (B7) is the backstop.
13. **The avatar upload waits for owner steps (D11).** Until the Cloudflare public avatar bucket, the token, the two params, the Secret Manager entries and `firebase deploy` exist, `DataResidencyPolicy.avatarsOnR2` stays `false`: nothing is signed, uploaded or enqueued and the avatar stays a local `file:` URL, exactly as today. A user with only a local account and no Firebase session cannot call `signAvatarUpload` (it needs `requireUid`) and keeps the local avatar (A26).
14. **No confirm step and no server-side content check for avatars (accepted).** Mitigations: the signed content type `image/jpeg`, the 1 MB cap, one fixed object per uid, 10 requests per hour and App Check. The public URL contains the uid, which partners already see in invites. An orphan avatar object stays until the next overwrite or the account deletion (`purgeAvatar`). Cache residue after deletion (accepted): the object carries a signed one-year `immutable` `Cache-Control`, and the `?v=<nowMs>` URL only busts the cache on an overwrite. A copy fetched under an older `?v=` URL can therefore stay in a CDN cache and in Coil's disk cache for up to a year, even after a new upload or `purgeAvatar`. A custom domain on the public bucket (section 14) lets the owner purge the CDN; `r2.dev` URLs are rate-limited and not meant for production.
15. **Offline display of the user's own avatar (A33, UNVERIFIED on a device).** It depends on Coil honoring the signed immutable `Cache-Control` of the first online view. If not, the avatar shows the placeholder while offline until the next online view; no data is lost.
16. **The backup manifest is plain JSON** in `files/media` (titles, notes, dates and partner display names, no secrets, no e-mail, no tokens). It sits in app-private storage and travels only with the user's own Android backup, which 4i tells the user.
17. **Two sessions edit one tree.** T17 adds one separate `item` to `SettingsScreen` and T24 one hunk (`saveCoupleProfile`) to `InLoveViewModel` while the audit session edits other hunks of the same files. This plan's edits are exact-string `Edit` calls, which the tool refuses on a file that changed since it was read, so a clash on our side shows as a failed edit; the answer is to re-read and redo it. A whole-file write by the other session is the one case this cannot catch, so the final `git diff` review (T15) re-checks every hot file.
